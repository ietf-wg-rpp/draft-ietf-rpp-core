## Project Overview

This repository contains the IETF Internet-Draft for the **RESTful Provisioning
Protocol (RPP)** — `draft-ietf-rpp-core` (IETF stream, "Network
Working Group"). RPP is an HTTP/REST API for the provisioning and management of
objects in a shared registry database (domain names, hosts, entities), based on
EPP semantics ([RFC 5730] and the object RFCs). The document is authored in
Markdown for [mmark](https://mmark.miek.nl/) and compiled to XML (xml2rfc v3),
then to TXT, HTML, and PDF.

## Conventions

### Literals

**House style: plain inline code** — wrap every literal token (HTTP header name,
JSON key, type name, URN, enum/status value, result code, query parameter) in
single backticks with **no inner quotes**: `` `RPP-Cltrid` ``, `` `errors` ``,
`` `urn:ietf:params:rpp:error` ``, `` `02104` ``. Do **not** use the `` `"..."` ``
quoted-backtick style. Match the existing usage in the source when in doubt.

### Definition lists (structured object/field definitions)

Field and object definitions use the mmark definition-list idiom: a term line in
backticks, then one or more `: ` lines carrying cardinality, type, and prose.
Reproduce this shape exactly (note the blank line between entries):

```markdown
`type`
: (required, string) This field MUST always contain the fixed string value `urn:ietf:params:rpp:error` ...

`errors`
: (optional, array of error objects) MUST contain objects detailing ...
```

Some shorter field lists in the draft use indented `-` bullets with
`name (REQUIRED):` prefixes instead (e.g. the `RPP-Authorization` fields in
**Request Header Fields**).
When editing within a section, follow whichever form that section already uses
rather than converting it.

### Cross-references and anchors

- **Anchor:** `{#anchor}` — either trailing a heading, or on its own line as a
  block anchor attached to the following block. The draft currently has exactly one
  anchor, `{#profile-example}` (a block anchor on a JSON example in §Definition); it
  uses no heading anchors. The Anchor column in the Document Index is therefore
  empty — the index script does pick up trailing-heading anchors if any are added.
- **Reference:** `(#anchor)` inline — e.g. `see (#profile-example)`.
- Keep anchors stable; never silently rename or drop one during a restructure.

### Citations / references

- **Normative:** `[@!RFCxxxx]`. **Informative:** `[@RFCxxxx]`. Section form:
  `[@!RFC9110, Section 16.4.2]` (and the bare textual form `[RFC5731, Section 2.3]`
  also appears). Classify each new reference normative vs. informative deliberately.
- Well-known **RFCs auto-resolve** from the citation tag — no local entry needed.
- **Non-RFC references** are hand-written `<reference anchor="..." target="...">…</reference>`
  RFCXML blocks **after `{backmatter}`** (currently: `REST`, `YAML`, `SemVer`, `XML`).
  Cite them with `[@!ANCHOR]` / `[@ANCHOR]`. Preserve the exact RFCXML when editing.

### Code / example blocks

Use fenced blocks with a language hint matching existing usage: `json` (request/
response bodies, Problem Details), `http` (request/response examples), `abnf`
(syntax fragments), `dns` (SRV records). xml2rfc renders these as
`<sourcecode>`/`<artwork>`.

### RFC 2119 / 8174 requirement keywords (markup)

Keywords are written in **bare all-caps** in the prose (e.g. `MUST`, `SHOULD`,
`MAY`) — no bold markup. The normative *meaning* is governed by the Conventions
section. **Note:** that section currently cites only RFC 2119 and lists nine
of the BCP 14 keywords (it omits `NOT RECOMMENDED` and the RFC 8174 "…only when in
all capitals" sentence). If asked to tighten the boilerplate, propose updating it
to the full BCP 14 form citing **both** RFC 2119 and RFC 8174.

## Writing Style

IETF specifications have a distinct, conservative house style. Apply it to all
prose you add or edit. The goal is a document an independent implementer can turn
into interoperable code without guessing.

### Normative language (RFC 2119 / BCP 14)

- Use **MUST / MUST NOT / REQUIRED / SHALL / SHALL NOT / SHOULD / SHOULD NOT /
  RECOMMENDED / NOT RECOMMENDED / MAY / OPTIONAL** only in their RFC 2119 sense and
  **only in all-caps**. Lowercase = ordinary English, no normative force.
- Every keyword places a requirement on a **specific actor** (RPP client / RPP
  server) for a **specific, testable behaviour**. "The server MUST reject the
  request" is testable; "the system MUST be secure" is not.
- Don't stack keywords; don't use a keyword where plain present tense states a fact
  ("the header contains the result code", not "MUST contain").
- Reserve **SHOULD** for genuine implementer discretion and say what to weigh; if
  there is no legitimate reason to deviate, it is a **MUST**.
- State **error handling and behaviour on malformed/unexpected input** explicitly
  — for RPP that means the HTTP status code, the `RPP-Code` header, and the Problem
  Detail body together (see **Problem Detail responses for errors** and **Result Codes**).

Per the IESG Statement on Clarifying the Use of BCP 14 Key Words
(<https://www.ietf.org/about/groups/iesg/statements/clarifying-use-bcp14/>):

- **Use the key words sparingly** — only where required for interoperability or to
  limit behaviour with potential for harm. They are not for emphasis.
- A normative statement does **not** need a key word; plain declarative prose is
  often clearer and equally normative.
- **Justify every SHOULD / RECOMMENDED** — spell out the consequence of deviating
  and what a conformant implementation must consider.
- For **backward/EPP-compatibility** requirements (a recurring RPP theme), make the
  rationale explicit, e.g. "New implementations MUST use $NEW; implementations
  SHOULD accept $OLD for compatibility with existing deployments."
- **Do NOT use BCP 14 key words** in the Abstract, IANA Considerations, examples,
  figures/captions, or appendices.

### Specify, don't describe

- Write **declarative, present-tense** requirements naming the **conformance
  target** (RPP client / RPP server). Specify **both sides** — what a generator
  produces and what a parser must accept, including handling of unrecognised
  values (forward-compatibility / must-ignore).
- Give the **wire format precisely**: HTTP method, URL/URI template, headers,
  media type, JSON structure, character encoding, case sensitivity, length limits,
  defaults, and units. Prefer explicit enumerations and ranges over vague adjectives.
- Keep endpoint behaviour consistent with **HTTP Mapping Rules**: endpoints
  are *derived* from those rules plus the data objects, so specify the rule, not a
  one-off URL, where possible.

### Terminology discipline

- Define each term **once** in §Terminology and use it **consistently** — never
  introduce a synonym for a defined term (use "RPP client"/"RPP server" throughout,
  not "consumer"/"endpoint").
- Reuse terminology from existing RFCs (RFC 9110 for HTTP, RFC 5730 et al. for EPP,
  RFC 8499 for DNS) rather than reinventing it; cite the source.
- **Expand every acronym on first use** in both body and titles. RFC 7322 exempts
  well-known abbreviations (TCP, IP, HTTP, …); RPP, EPP, JWT, URN, etc. should be
  expanded on first use.

### Structure and cross-references

- Lead each major section with a one-sentence purpose statement.
- Put rationale/history in non-normative places (Introduction, notes, appendices);
  keep the normative body tight and mark examples as non-normative/illustrative.
- Cross-reference with `(#anchor)` instead of duplicating a requirement — duplicated
  normative text drifts out of sync.

### Document structure and required sections (RFC 7322)

Follow RFC 7322 ordering. Current structure: Abstract → Introduction →
Terminology → Conventions → (technical body) → IANA Considerations →
Internationalisation Considerations → Security Considerations → Change History →
Acknowledgements, then `{backmatter}` references. Section-specific rules:

- **Abstract** — standalone; **no citations or references**; do not duplicate the
  Introduction.
- **IANA Considerations** — required; list every registry action precisely
  (RPP defines several new registries: discovery, extension, profile, result codes,
  and a media type). Use `TBD1`, `TBD2`, … for IANA-assigned values; never leave a
  bare TODO at submission.
- **Internationalisation Considerations** — keep substantive given RPP
  carries human-readable registration data.
- **Security Considerations** — **required and substantive**: threat model,
  what RPP does/doesn't protect, residual risk. Follow BCP 72 (RFC 3552). RPP
  currently mandates TLS 1.3 [RFC 8446] and references RFC 9325; keep that current.
- **Privacy Considerations** — RPP provisions registration data that can identify
  people (registrant contacts, etc.). If asked to expand the security/privacy text,
  consider whether a dedicated Privacy Considerations section per RFC 6973 is
  warranted, and raise it rather than silently omitting.
- **References** — split Normative / Informative, ordered by tag, no intro prose.
  Citation tags contain no spaces.

### Tone and mechanics

- Neutral and precise; avoid hype and hedging ("simply", "just", "obviously").
- "i.e." vs "e.g." are not interchangeable; "e.g." lists are non-exhaustive.
- One requirement per sentence where possible (enables conformance checklists).
- Spell prose in **UK English** consistently; protocol elements and literals keep
  their US spelling (see Pre-Release Review → Check 3). Use the serial (Oxford)
  comma — the IETF default.
- Title-case the document title and section titles.
- **Use reserved example identifiers** (RFC 2606 / BCP 32): this draft uses
  `rpp.example` as the server host and `https://rpp.example/...` in examples — keep
  using `.example` / `example.com` / `example.net`, never real domains or addresses.
- Wrap bare URIs in angle brackets (`<https://example.com/>`).
- When in doubt about style: RFC 7322 (Style Guide), <https://authors.ietf.org/>,
  and for keywords RFC 2119, RFC 8174, and the IESG BCP 14 statement above. Run
  **idnits** (or the datatracker submission checks) before submitting.

### Writing Change History Entries

Each substantive edit gets a bullet under the current draft revision's `=== Change from … to …` heading (create the heading for the new revision if it does not yet exist).

Keep entries **terse**: state the action and point to the affected section by cross-reference, then stop. Do **not** append a summary of what the section now says or why the change was made — the cross-referenced section is the source of truth for that detail.

- Pattern: `<Verb> <<anchor,format=title>> to/in <<section-anchor,format=title>>.` (e.g. `Added`, `Clarified`, `Removed`, `Restructured`).
- Reference sections with `<<anchor,format=title>>`, not by literal title text, wherever an anchor exists.
- One bullet per logical change. Do not fold rationale, threat descriptions, or normative detail into the bullet.
- Good: `- Clarified handling of multiple `"_domainconnect"` TXT records in <<dns-provider-discovery,format=title>>.`
- Avoid: `- Clarified handling of multiple `"_domainconnect"` TXT records in <<dns-provider-discovery,format=title>>: invalid records are rejected, at least one valid record is processed, and the Service Provider MAY iterate…` (trailing explanation belongs in the section, not the history).

## Edit Workflow

**CRITICAL**: All edits to the source document MUST follow this workflow.

**CRITICAL — Never restore manually-removed content**: If the user has edited or
removed content directly in the source file, NEVER re-add, restore, or reintroduce
it — not in a later edit, not inside a larger replacement block, not while "fixing"
something nearby. The user's manual edits are authoritative. Re-read the region if

**CRITICAL — Bulk structural edits MUST be scripted**: Any change repeating the
same structural transformation across many places (converting a list to a
definition list, re-quoting every literal, rewrapping every entry) MUST be done
with a throwaway script (`.work-*.py` or similar), NOT a series of hand-written
`Edit` calls. The script:

- **Transforms structure only, never rewrites prose** — parse and re-emit cells/
  lines verbatim; only markup may change.
- **Is verified before trusting it** — snapshot first
  (`cp src/draft-ietf-rpp-core.md /tmp/before`), run, then diff and confirm only
  the intended structural tokens changed and **zero prose words** changed. Preserve
  all anchors.
- **Respects manual edits** — drive off current file state; skip already-converted entries.
- **Is deleted afterward** (and its snapshot). Do not commit `.work-*.py`.

Still follow propose-and-approve below before running any script on the live draft.

## Pre-Release Review

Run this process **only when the user asks for a final pre-release review**
(e.g. before submitting a new revision to the datatracker). It is a whole-document
pass, so it is the one case where every section is read — still in
`offset`/`limit` chunks guided by the Document Index, never in a single read.

### Process

1. **Prepare.** Run `./update-index.sh` and read `.agent-index.md`. Run the IANA
   consistency script (`cd src && python3 ../.scripts/check_iana_consistency.py`)
   as a baseline and note its result. Check `git diff` for uncommitted manual
   edits (e.g. to the title block) — they are the user's and are authoritative.
2. **Read and collect (read-only).** Read the title block and Changes History,
   then the whole body, IANA Considerations, and backmatter in chunks of a few
   hundred lines. Note findings as you read; apply nothing.
3. **Mechanical sweeps.** Complement the reading with greps for things that are
   easy to miss by eye: trailing whitespace, non-ASCII characters, semicolons in
   prose, mixed-case BCP 14 keywords (`MUST not`, `Must`, `MAY not`), citations
   without `@` (`[RFCxxxx]`), cited references vs references defined in the
   backmatter, `(#anchor)` targets without a matching `{#anchor}`, US spellings,
   `TODO`/`TBD`/`TBC` notes and HTML comments, and first use of acronyms.
4. **Cross-check what the script does not.** The IANA script compares elements
   and operations, but also verify by hand: `Extends` values, operation
   identifiers present on every IANA operation, and element descriptions whose
   meaning (not only wording) differs between normative text and IANA.
5. **Number the findings.** Use one ID per issue (split grouped findings so each
   can be approved individually):
   * `Mxx` — Check 1 (header metadata).
   * `Hxx` — Check 2 (Changes History).
   * `Sxx` — Check 3 (spelling and UK/US consistency).
   * `Cxx` — Check 4 (whole-document consistency), grouped under subheadings
     (substantive defects, citations and references, BCP 14, open items and
     placeholders, style and mechanics), most severe first.
6. **Record the to-do list.** Write the findings to `.work/review_YYYYMMDD.md`
   (date of the review) as a checklist: one line per ID with line number(s),
   current text, and proposed fix. Note at the top that line numbers refer to
   the file state at review time, and record the IANA script baseline.
   Legend: `[ ]` open, `[x]` applied, `[-]` rejected, `[>]` deferred; mark
   approvals inline as `(approved)`.
7. **Present.** Show the findings to the user grouped by the four checks, with
   the same IDs. Flag findings that rename wire identifiers (element or
   operation identifiers, IANA entries) as needing an explicit decision.
8. **Apply on approval only.** Apply nothing until the user approves specific
   IDs or ranges (Edit Workflow, Steps 1–2). Repeated mechanical fixes (e.g. the
   same spelling change in many places, trailing whitespace) MUST be applied
   with a verified throwaway script, per the bulk-edit rule above. Substantive
   findings get exact proposed wording first.
9. **Keep the to-do file current.** After every approval, application,
   rejection, or deferral, update the item's state in
   `.work/review_YYYYMMDD.md`. After applying edits, run `./update-index.sh`,
   re-run the IANA script, and add Changes History entries where the edit is
   not itself a Changes History fix.

hyphenation/capitalisation of recurring terms (e.g. "nameserver" vs
"name server", "lowercase" vs "lower case", "offline review" vs
"offline-review", "Uniform Interface" vs "Uniform interface", constraint
placeholders `(None)` vs `None` vs `-`, title case in headings). A tool such as
`aspell --lang=en_GB` or `hunspell -d en_GB` can be used to generate candidates
if available, but every candidate MUST be checked against the literal/quotation
exceptions above before it is proposed.

### Check 4 — Whole-Document Consistency Scan

Scan the full document for inconsistencies, including:

- **Object model:** stray or duplicated attribute bullets; elements referenced
  in prose (operations, constraints, examples) that no longer exist; content
  left over from earlier restructurings that contradicts the Changes History;
  `Extends`, identifiers, cardinality, or meaning differing between normative
  definitions and IANA tables; inconsistent operation identifiers across
  similar objects; the same requirement stated in two places.
- **Status models:** status values, exclusions, transition diagrams, state
  descriptions, and the corresponding IANA registries agree, and equivalent
  rules are stated consistently across objects.
- **Terminology:** defined terms (Conventions and Terminology) used
  consistently, without synonyms (e.g. "Data Object" vs "resource object") or
  EPP-only wording where RPP terms exist; acronyms expanded on first use.
- **Cross-references and citations:** broken or dangling `(#anchor)`
  references; references written without `@` (not rendered as citations);
  cited documents missing from References and defined references never cited;
  normative/informative classification that looks wrong (e.g. an informative
  reference that a MUST depends on); figure/table captions and anchors.
- **BCP 14:** mixed-case or non-keyword forms (`MUST not`, `MAY not`, `Must`);
  key words used as plain adjectives ("OPTIONAL elements"); key words in the
  Abstract, IANA Considerations, examples, or appendices.
- **Open items:** leftover `TODO`, `TBD`, `TBC` editor notes (including ones
  made stale by later changes), commented-out text, empty sections, IANA
  placeholders other than `TBDn`, and missing required sections (Security
  Considerations, Privacy Considerations where personal data is handled).
- **Mechanics:** semicolons in prose, non-ASCII characters, trailing
  whitespace, double spaces, missing blank lines before lists, example
  domains not using reserved names.

Report findings only; do not restructure or rewrite prose beyond the minimal fix
for each finding.
